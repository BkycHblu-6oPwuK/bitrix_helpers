# Журнал архитектурных решений (ADR)

Формат: краткие записи «контекст → решение → следствия».

---

## ADR-001. Расширение SDK внутри модуля, а не форк vendor

**Контекст.** SDK `apiship/apiship-sdk-php` неполный (нет webhooks, connections,
externalTracking, lists/statuses и др.). Форк в `vendor/` теряется при `composer update`.

**Решение.** Все доработки — в `lib/Sdk/` модуля, наследуя классы SDK. Фасад
`ExtendedApiship` добавляет недостающие группы методов.

**Следствия.** vendor остаётся обновляемым; при мажорных изменениях SDK правим только `lib/Sdk/`.

---

## ADR-002. Хранение — собственные ORM-таблицы, без HLBlock

**Контекст.** Нужно хранить связь заказ Bitrix ↔ заказ ApiShip, лог статусов, лог вебхуков.

**Решение.** ORM `DataManager`-таблицы с префиксом `beeralex_apiship_`
(`_order`, `_status_log`, `_webhook_log`). Создание/удаление через `TableManagerTrait`.

**Следствия.** Полный контроль схемы и запросов; нет зависимости от highloadblock.

---

## ADR-003. Настройки — Options + .env

**Контекст.** Минимум настроек в админке, секреты не в БД под контролем версий.

**Решение.** `Options extends AbstractOptions` (isTest, logs, ssl, defaultProviderConnectId,
статус-триггер отправки). Токен доступа — из `.env` (через `Beeralex\Core\Config\Config`).

**Следствия.** Секрет не попадает в дамп настроек; окружения переключаются через `.env`.

---

## ADR-004. Профили доставки — гибрид

**Контекст.** Нужен «1 обработчик, максимум управления из ЛК ApiShip», но по-битриксовому
через профили служб доставки.

**Решение.** Один класс `ApiShipProfile` (isProfile=true). В CONFIG профиля хранятся
`providerKey` и `tariffId`. Список доступных ТК/тарифов подтягивается динамически из
`lists/providers` (+ `lists/tariffs`). Профили можно завести под нужные ТК, не плодя классы.

**Следствия.** Минимум кода; гибкая привязка к ТК; данные ТК всегда актуальны из API.

---

## ADR-005. Момент отправки заказа в ApiShip — по настраиваемому статусу

**Контекст.** Не слать в ApiShip черновики/неоплаченные заказы.

**Решение.** В настройках модуля выбирается статус заказа Bitrix. При переходе заказа в этот
статус (`OnSaleStatusOrderChange`) вызывается `OrderService->create()`.

**Следствия.** Контроль момента интеграции; поведение настраивается без правки кода.

---

## ADR-006. Создание заказа асинхронное + вебхуки

**Контекст.** SDK поддерживает `create` (async) и `createSync`.

**Решение.** По умолчанию `create` (async). Итоговый статус/номер провайдера приходит вебхуком
и обновляет `beeralex_apiship_order`.

**Следствия.** Меньше таймаутов при оформлении; нужна работающая подписка на вебхуки.

---

## ADR-007. Идемпотентность вебхуков

**Контекст.** ApiShip может доставлять один вебхук повторно.

**Решение.** Таблица `beeralex_apiship_webhook_log` с уникальным ключом по event/tracing id.
Повторные события отбрасываются до обработки.

**Следствия.** Нет двойной смены статусов/дублей записей в логе.
